# ADR-0005：渠道模型目录的同步策略

- **日期**：2026-09-18
- **状态**：已采纳并上线（镜像 `niannian-sd2:billing-20260918-r2`）
- **决策人**：老大
- **相关**：ADR-0001（渠道选型）、R8（模型 ID 会失效）、R27

---

## 背景

紫域（ziyuai.vip）的模型目录是**动态下发**的：54 个 `zy_model_*`，会下线、会变价。
审计时确认过：历史任务里出现过 `model not found` / `unavailable`。

改造前 `listZiyuModels()` **没有任何缓存**，`fetch` 用 `cache: "no-store"`，
意味着：

- 用户每打开一次工作台 → 实时打一次紫域；
- **每次下单还要再打一次**（`app/api/ziyu/jobs/route.ts` 要用它校验 `modelId`）。

后果是**强耦合**：紫域抖一下（超时、429、503），我们不是"模型列表稍微旧一点"，
而是**工作台打不开、下单直接 502**。上游的可用性直接等于我们的可用性。

## 决策

采用 **快照 + 实时兜底（stale-while-revalidate 思路）**：

| 情况 | 行为 |
|---|---|
| 快照新鲜（< TTL） | 直接返回快照，**零上游依赖** |
| 快照过期 | 实时拉上游；成功则更新快照 |
| 上游失败 | **退回旧快照**并标记 `stale`，降级但不阻断下单 |
| 从没成功过（冷启动即失败） | 只能抛错（没有快照可退） |

- **TTL = 600 秒**（10 分钟），可用 `ZIYU_MODEL_TTL_SECONDS` 覆盖。
- **并发去重**：快照过期时若同时涌入多个请求，只放行一个去拉上游（in-flight promise），避免雪崩。
- **状态外化**：`ziyuModelSyncStatus()` 暴露 `synced / stale / modelCount / ageSeconds / ttlSeconds`，
  并通过 `/api/providers` 的 `ziyu.modelSync` 返回；`stale` 时 `state` 从 `ready` 降为 **`degraded`**。

## 为什么不是另外两种

- **纯定时快照**（过期就只用旧数据、上游挂也不管）：更简单，但上游挂超过一个周期后
  数据会持续陈旧且**没有任何信号**，运维无从感知。
- **保持全实时**：一致性最好，但把我们的可用性抵押给了上游——这正是要解决的病。

## 代价与边界

- 模型下线/变价最多滞后 **10 分钟**被感知。若选到刚下线的模型，下单仍会失败，
  但会走到退款分支（全额退），用户不受损失。
- 快照是**进程内存**（`globalThis`），容器重启即失效，冷启动第一次会实时拉。
  多实例部署时各实例各自持有快照（当前是单实例，不构成问题）。
- 不落库：模型目录不做历史归档。如果以后要审计"哪个模型什么时候下线"，再加。

## 验收（2026-09-18 实测）

```
第一次调 /api/providers：modelSync = {synced:true, stale:false, modelCount:54, ageSeconds:0, ttlSeconds:600}
立刻再调一次          ：耗时 24ms（命中快照，不再打上游）
```

## 回滚

把 `ZIYU_MODEL_TTL_SECONDS=0` 配成极小值即可近似回到全实时（无需改代码）；
彻底回退则 revert `lib/ziyu-api.ts` 的 `listZiyuModels` 实现。
