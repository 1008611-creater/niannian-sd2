# 念念 AI 视频工作台：高效生产规则

## 唯一目标

尽快交付用户能在网站中播放、下载或使用的真实视频结果。

固定路线：

`当前真实状态 -> 最早缺失步骤 -> Harness（流程治理框架）-> 一个主 Skill（专业方法技能）-> Provider（模型或服务提供方）-> 用户可用结果`

Harness 只保存当前任务、当前 owner、下一动作和改变结果的证据；Skill 只提供生成与媒体方法。两者不应生成额外的流程、状态流或聊天噪声。

## 直接推进

- 一个任务、一条写入路径、一个当前动作；没有实际冲突时不增加 lease、队列、子任务或审批层。
- 每一步完成后自动进入下一缺失步骤。代码、测试、Worker claim、预检、上传、任务 ID、Provider 提交和下载都只是进度，直到用户可用的真实结果出现。
- 使用当前任务已有授权；同一个明确且有上限的 Provider 动作不重复确认。
- 有利于速度且写集隔离的准备、检查或验收可以并行；不要为“可能出问题”创建第二条生产路线。
- 任务不能因内部阶段完成而停下。若有下一个自动动作，直接继续；若确实需要用户决定，才报告一次精确问题。

## 只保留已证实的门

禁止预设式保守：没有当前证据，不得因可能的费用、Provider、登录、部署、隐私、恢复或质量风险阻塞任务。

新增或保留门只限两种情况：用户明确要求；本项目已发生的具体失败。每个门必须写明触发证据、保护动作和退出条件；问题消失即删除。优先修复发生故障的那一行或接口，不要升级成永久制度、重复确认、重复复核、watchdog、心跳或多层状态机。

## 低噪声回传

任务管理线程只向主控回传三类外部事件：

- `user_action_blocked`：确实需要用户动作且自动恢复已经无路可走。
- `user_acceptance_required`：真实可见结果已就绪，且仅剩用户选择。
- `delivery_completed`：用户路径已实际可用。

其他实现、测试、验收、心跳、claim、轮询和内部修复都留在本地，不发给用户，也不制造新的主控任务。主控收到内部完成后自动继续；任务线程若意外 idle，主控只恢复一次同一 `next_action`，不得新建或重复提交。

## 最小验证

每次代码、脚本、工作流或部署改动后，运行最小的检查来证明改动路径实际执行，确认结果内容不是空壳或旧产物。报告只说明已验证的真实结果和仍未执行的最后一步。

最终交付只看用户入口：网站上的视频能够实际播放或下载，或用户明确指定的业务结果已经发生。不要把过程状态当成交付。
